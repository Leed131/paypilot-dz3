## Ручні додаткові перевірки retrieval

Знаменник recall — потрібні факти; precision — усі повернення фрагментів, включно з повтореннями. Релевантність тут суворо до запитаних фактів, а не загальної теми.

| Case lesson-04 | Recall | Precision | Пояснення |
|---|---|---|---|
| H01 | 0 з 6 = 0 | 0 з 4 = 0 | 3 спреди та 3 allowance; загальний FX guide не містить значень. |
| H02 | 4 з 6 = 0.667 | 6 з 12 = 0.5 | 5 ідентифікаторів + 60 днів; #b2 містить перші 3 коди і строк. |
| H03 | 0 з 2 = 0 | 0 з 1 = 0 | Потрібні обидва числові компоненти; fragment лише каже, що їх два. Faithfulness двох числових тверджень: 0 з 2 = 0; не оцінка всього тексту. |
| H04/H05 | — | — | Пошуку немає, правильний текст не замінює retrieval. |
| H06 | 2 з 2 = 1 | 2 з 7 = 0.286 | Два повернення #b3 містять потрібні ліміти; інші — ні. Faithfulness двох чисел 2 з 2 = 1. |
| H07 | 0 з 1 = 0 | 0 з 12 = 0 | Жоден fragment не містить запитаний строк 56. |
| H08 | 1 з 1 = 1 | 1 з 1 = 1 | settled є у disputes-process#b1; faithfulness відповіді 1 з 1 = 1. |

H09/H10 не зводимо до одного неаргументованого бала: окремо оцінено факт, цілісність цитати та збіг literal. Помилкове цитування може існувати поруч із правильним загальним правилом.

## Межі й наступна зміна тестів

Результати заморожено. Для наступної версії набору окремим комітом: перевіряти факт виклику пошуку/отримані факти, розвести semantic correctness і verbatim quotation, перевіряти всі заборонені побічні дії та додати бюджет повторних викликів. Не виправляти старий результат новим oracle заднім числом. H04/H05 — конкретний приклад хибного висновку «retrieval PASS означає retrieval працює».

Runner.py кіту зберігає `answers: [r["answer"][:400] ...]`. Тому багато старих відповідей і H01/H10 обрізано; вердикти виконані на результаті до збереження, але raw не дає повної стенограми для довільної повторної семантичної оцінки. Tool.result.fragments у цих JSON повні. Model/provider і input/output окремо у raw не збережено; judge_model=not-used — не назва моделі агента.
